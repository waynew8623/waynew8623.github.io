<p>在上一篇教程中，我们通过 Docker 成功<a href="https://waynetalk.com/493/">部署了 VLESS-Reality 节点</a>。在配置模板中，大家都会填写一个伪装目标（<code>server_name</code> / <code>SNI</code>）。</p>
<p>不少人部署后可能会遇到以下怪象：</p>
<ul>
<li>明明配置无误，客户端偶尔会报 <code>TLS handshake failed</code> 或超时；</li>
<li>照抄网上教程用了热门域名（如 <code>[www.apple.com](https://www.apple.com)</code>、<code>gateway.icloud.com</code>），用了一两周端口突然“神秘失联”；</li>
<li>某些地区网络秒连，换到另一个运营商却打不开网页。</li>
</ul>
<p>问题的核心往往出在 <strong>SNI 伪装域名的选择</strong> 上。Reality 的核心机制是“借壳伪装”，如果借的“壳”本身存在破绽，审查系统的主动探测（Active Probing）就会瞬间拆穿伪装。</p>
<p>本文将深入解析 Reality 的握手回落逻辑，揭示常见域名的四大致命雷区，并提供一套工业级的伪装域名自动化筛选方案。</p>
<hr />
<h2>一、 Reality 为什么需要“借壳伪装”？</h2>
<p>要选对域名，首先要理清客户端、审查系统与目标站点之间的交互逻辑。</p>
<pre><code class="line-numbers">[客户端] ──── (带合法认证签名 + SNI: a.com) ────> [你的 VPS (Reality)] ────> 放行并解密科学流量
                                                         │ (无认证/探针伪造)
                                                         └─── 回落转发 ───> [真正的 a.com (真实服务器)]

</code></pre>
<ol>
<li><strong>合法客户端握手</strong>：<br />
客户端在向你的 VPS 发起 TLS Client Hello 时，携带着指定域名的 SNI 以及通过你预设私钥计算出的认证信息。VPS 校验通过后，双方建立加密通道。</li>
<li><strong>主动探测触发回落</strong>：<br />
审查系统（GFW）检测到未知的 443 端口流量时，会假冒常规浏览器发送标准的 TLS 探测包（探针）。由于探针没有合法的签名，Reality 服务端会立即触发<strong>回落机制（Fallbacks）</strong>——它会作为透明反向代理，把探针的数据包完全转发给目标站点的真实服务器，并将真实服务器的响应原路返回给探针。</li>
<li><strong>探针判定</strong>：<br />
探针检查收到的 TLS 证书、公钥链条、HTTP 响应头、甚至网页源码，发现与公网访问 <code>a.com</code> 完全一致，从而认定“这台 VPS 只是一个正常的反向代理或 CDN 节点”，放弃拉黑。</li>
</ol>
<p><strong>破绽在哪里？</strong><br />
一旦你的 VPS 与伪装的目标服务器之间存在<strong>证书协议不匹配、网络物理跳数异常、或者域名在国内已被阻断</strong>，探针就会立刻判定你的行为是恶意伪装。</p>
<hr />
<h2>二、 伪装域名筛选的四大致命雷区</h2>
<p>很多新手随手从网上找域名，容易踩中以下陷阱：</p>
<h3>雷区 1：使用国内大厂或 gov/edu 域名</h3>
<ul>
<li><strong>反常识</strong>：有人认为国内大厂（如腾讯、阿里）延迟低，拿来做伪装最好。</li>
<li><strong>致命后果</strong>：国外 VPS 的 IP 地址，怎么可能持有国内严格备案域名的真实证书？审查系统拥有中国大陆境内域名的权威解析库和 IP 归属库，境外 IP 伪造境内大厂域名属于“不打自招”。</li>
</ul>
<h3>雷区 2：使用已被 GFW 阻断或 DNS 污染的域名</h3>
<ul>
<li><strong>反常识</strong>：直接拿 Google、Twitter、YouTube 域名来当 Reality 伪装。</li>
<li><strong>致命后果</strong>：既然这些域名在境内本来就无法直接解析或直连，你发往 VPS 的 Client Hello 报文里却大摇大摆地写着被墙域名的 SNI，网关层级的 SNI 阻断机制会在第一秒直接掐断连接。</li>
</ul>
<h3>雷区 3：目标域名不支持 TLS 1.3 或不支持 HTTP/2</h3>
<ul>
<li>Reality 要求目标域名必须支持 <strong>TLS 1.3</strong> 且最好支持 <strong>h2 (HTTP/2)</strong>。如果目标域名只支持老旧的 TLS 1.2，握手特征与现代主流浏览器完全脱节，极易被统计学特征标记。</li>
</ul>
<h3>雷区 4：目标站点采用了复杂的 GeoDNS 导致多 IP 分流</h3>
<ul>
<li>知名国际跨国站点（如部分 Apple 节点）在国内和国外解析出的 CDN 节点完全不同。</li>
<li>如果探针直接从国内请求该域名得到的是上海节点证书，但你的 VPS 从海外回落转发拿到的是法兰克福节点证书，证书指纹不一致会直接暴露中继行为。</li>
</ul>
<hr />
<h2>三、 优质伪装域名的黄金法则</h2>
<p>一个理想的 Reality 伪装域名，必须满足以下硬性条件：</p>
<ol>
<li><strong>国内直连无阻断</strong>：国内各大运营商网络均可顺畅直连，没有 DNS 污染和 SNI 干扰。</li>
<li><strong>机房同地域/低跳数</strong>：伪装站点的物理机房最好与你的 VPS 处于同一国家或地区（例如：美西 VPS 伪装在美西本地站点），确保回落延迟低于 50ms。</li>
<li><strong>原生支持 TLS 1.3 + HTTP/2</strong>：证书链条完整有效，采用主流加密套件。</li>
<li><strong>业务性质合规且冷门</strong>：</li>
</ol>
<ul>
<li><strong>优选</strong>：境外高校开源镜像站、国际知名开源软件官网、区域性外企官网、海外大型 Linux 发行版镜像源。</li>
<li><strong>避免</strong>：烂大街的超热门公开教程域名（避开群体特征）。</li>
</ul>
<hr />
<h2>四、 实战：手动与自动化检测伪装域名</h2>
<p>不要凭感觉猜域名，必须用工具进行严格校验。</p>
<h3>1. 验证目标域名是否支持 TLS 1.3 与 HTTP/2</h3>
<p>在你的 VPS 上运行以下 <code>curl</code> 测试命令：</p>
<pre><code class="language-bash line-numbers">curl -Iv https://<目标域名> --http2

</code></pre>
<p><strong>观察输出结果</strong>：</p>
<ul>
<li>必须包含：<code>SSL connection using TLSv1.3</code></li>
<li>必须包含：<code>ALPN: server accepted h2</code> (或 http/1.1)</li>
<li>HTTP 状态码通常应为 <code>200</code>、<code>301</code> 或 <code>302</code>。</li>
</ul>
<h3>2. 测试 VPS 到目标站点的握手延迟</h3>
<p>在 VPS 上直接探测与目标站点的网络连通性：</p>
<pre><code class="language-bash line-numbers">time curl -so /dev/null https://<目标域名>

</code></pre>
<p>耗时最好在 <strong>0.1 秒到 0.3 秒以内</strong>。如果回落延迟过高，客户端在首次建连时会有明显的卡顿感。</p>
<h3>3. 一行命令自动化批量扫描优质 SNI</h3>
<p>你可以使用针对 Reality SNI 筛选的开源脚本或基于 Docker 运行检测工具。在 VPS 上执行以下脚本，即可快速批量探测一组域名的合格率：</p>
<pre><code class="language-bash line-numbers"># 测试候选域名列表
DOMAINS=(
  "dl.google.com"
  "images.unsplash.com"
  "cdn.jsdelivr.net"
  "aws.amazon.com"
  "www.lovelive-anime.jp"
  "mirrors.kernel.org"
)

for domain in "<span class="katex math inline">{DOMAINS[@]}"; do
  echo "正在检测:</span>domain ..."
  # 检查 TLS 1.3 与 HTTP/2
  result=<span class="katex math inline">(curl --connect-timeout 3 -m 5 -Iv "https://</span>domain" --http2 2>&1)
  if echo "<span class="katex math inline">result" | grep -q "TLSv1.3" && echo "</span>result" | grep -q "ALPN.*h2"; then
    echo "  [OK] <span class="katex math inline">domain 符合标准 (支持 TLS 1.3 与 H2)"
  else
    echo "  [FAIL]</span>domain 不符合要求"
  fi
done

</code></pre>
<hr />
<h2>五、 将优选域名应用到服务端与客户端</h2>
<p>筛选出满意的域名（假设为 <code>mirrors.kernel.org</code>）后，更新配置并热重载：</p>
<h3>1. 更新 <code>config.json</code></h3>
<p>将 <code>/opt/sing-box/config.json</code> 中的相关字段替换：</p>
<pre><code class="language-json line-numbers">{
  "tls": {
    "enabled": true,
    "server_name": "mirrors.kernel.org",
    "reality": {
      "enabled": true,
      "handshake": {
        "server": "mirrors.kernel.org",
        "server_port": 443
      },
      "private_key": "<你的私钥>",
      "short_id": [
        "<你的ShortId>"
      ]
    }
  }
}

</code></pre>
<h3>2. 重启容器生效</h3>
<pre><code class="language-bash line-numbers">cd /opt/sing-box && docker compose restart

</code></pre>
<h3>3. 客户端同步修改</h3>
<p>将客户端节点的 <strong>SNI (Server Name)</strong> 同样修改为 <code>mirrors.kernel.org</code>。注意：<strong>服务端配置的 server_name 与客户端配置的 SNI 必须完全一致</strong>，否则握手将直接失败。</p>
<hr />
<h2>总结与建议</h2>
<p>伪装域名的选择决定了 Reality 节点生命周期的长短。牢记三点准则：</p>
<ol>
<li><strong>绝不使用境内域名与被墙域名</strong>；</li>
<li><strong>VPS 与伪装目标机房距离越近越好</strong>；</li>
<li><strong>避开网上教程公开发布的“大通铺”域名，通过探测脚本打造属于自己的专属域名库</strong>。</li>
</ol>
