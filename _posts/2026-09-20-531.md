<p class="wp-block-paragraph">当 n8n 从「个人玩具」变成「承接订单、发票、客服的关键基建」，一次卡死或漏执行就是真金白银的损失。本文聚焦 <strong>n8n 生产环境</strong> 运维：用队列模式把执行与编排分离，Worker 水平扩容，Webhook 高并发不掉链，<a href="https://waynetalk.com/523/">并设计一条不漏报的错误告警流</a>。</p>

<h2 class="wp-block-heading">单机模式的瓶颈</h2>

<p class="wp-block-paragraph">默认 n8n 是「主从一体」：既处理 Webhook、又跑执行。并发一高就互相抢资源，一个重工作流能把全部请求拖慢。解法：<strong>队列模式（Queue Mode）</strong>。</p>

<h2 class="wp-block-heading">架构</h2>

<pre><code>          ┌── Worker 1 (n8n worker)
Webhook ──┤ Redis Queue ──▶ Worker 2
          └── Worker N（按需扩容）
                │
                └─ 失败任务 → <a href="https://waynetalk.com/524/">错误告警流（飞书/邮件）</a>
</code></pre>

<h2 class="wp-block-heading">第一步：切到队列模式</h2>

<p class="wp-block-paragraph"><code>docker-compose.yml</code> 关键环境变量（Main + Worker 共用）：</p>

<pre><code class="language-dotenv"># 队列模式开关
EXECUTIONS_MODE=queue
QUEUE_BULL_REDIS_HOST=redis
QUEUE_BULL_REDIS_PORT=6379
QUEUE_BULL_REDIS_PASSWORD=${REDIS_PASSWORD}

# 执行数据落库（而不是内存）
EXECUTIONS_DATA_SAVE_ON_SUCCESS=all
EXECUTIONS_DATA_SAVE_ON_ERROR=all
EXECUTIONS_DATA_PRUNE=true
EXECUTIONS_DATA_MAX_AGE=168
</code></pre>

<p class="wp-block-paragraph">新增 <strong>Redis</strong> 服务：</p>

<pre><code class="language-yaml">redis:
  image: redis:7-alpine
  restart: unless-stopped
  command: ["redis-server", "--requirepass", "${REDIS_PASSWORD}", "--appendonly", "yes"]
  volumes:
    - ./redis:/data
</code></pre>

<h2 class="wp-block-heading">第二步：拆分 Main 与 Worker</h2>

<p class="wp-block-paragraph"><strong>Main（只收请求/编辑）</strong>：</p>

<pre><code class="language-yaml">n8n-main:
  image: n8nio/n8n:latest
  command: webhook
  environment:
    - EXECUTIONS_MODE=queue
    - QUEUE_BULL_REDIS_HOST=redis
    # ... 其余同上
  ports: ["127.0.0.1:5678:5678"]
</code></pre>

<p class="wp-block-paragraph"><strong>Worker（可多副本）</strong>：</p>

<pre><code class="language-yaml">n8n-worker:
  image: n8nio/n8n:latest
  command: worker
  deploy:
    replicas: 3
  environment:
    - EXECUTIONS_MODE=queue
    - QUEUE_BULL_REDIS_HOST=redis
  # 不暴露 5678，纯执行
</code></pre>

<p class="wp-block-paragraph">用 <code>docker compose up --scale n8n-worker=5</code> 即可扩到 5 个 Worker。CPU 吃紧时加副本，线性提升吞吐。</p>

<h2 class="wp-block-heading">第三步：Webhook 并发处理优化</h2>

<p class="wp-block-paragraph">Webhook 请求由 Main 收、入队后由 Worker 异步执行（默认 <code>Response Mode</code> 即时返回）。要点：</p>

<ul class="wp-block-list">
<li><strong>即时响应</strong>：Webhook 节点设 <code>Respond Immediately</code>，别等执行完才回，避免调用方超时。</li>
<li><strong>并发上限</strong>：用 <code>EXECUTIONS_CONCURRENCY_PRODUCTION</code> 控制单 Worker 并发（如 <code>10</code>），防止单 Worker 被打爆。</li>
<li><strong>Nginx 调优</strong>：<code>worker_connections</code> 调大，<code>proxy_read_timeout</code> 设长，配合前文 WebSocket 配置。</li>
<li><strong>限流</strong>：外部调用方加令牌桶；n8n 侧可对高流量 Webhook 单独拆工作流，避免互相影响。</li>
</ul>

<h2 class="wp-block-heading">第四步：失败重试与死信</h2>

<p class="wp-block-paragraph">队列模式天然支持重试。在节点开 <code>Retry On Fail</code>：</p>

<ul class="wp-block-list">
<li><code>Max Tries</code>：3</li>
<li><code>Wait Between Tries</code>：指数退避（如 2000ms）</li>
</ul>

<p class="wp-block-paragraph">超过重试仍失败的进入「死信」观察。配合 <code>EXECUTIONS_DATA_SAVE_ON_ERROR=all</code>，失败详情可查。</p>

<h2 class="wp-block-heading">第五步：错误告警流设计（核心）</h2>

<p class="wp-block-paragraph">单独建一个「运维告警工作流」，订阅 n8n 自身事件。两种触发：</p>

<p class="wp-block-paragraph"><strong>方式 A：Error Trigger 节点</strong><br />
n8n 内置 <strong>Error Trigger</strong>，任意工作流抛错都会触发它：</p>

<pre><code>Error Trigger → 解析错误（工作流名/节点/错误信息）
             → 飞书/企业微信/邮件推送
             → 写错误日志表（便于统计高频失败）
</code></pre>

<p class="wp-block-paragraph">告警文案：</p>

<pre><code>❌【n8n 执行失败】
工作流：{{ <span class="katex math inline">json.workflow.name }}
失败节点：{{</span>json.execution.error?.node }}
错误：{{ <span class="katex math inline">json.execution.error?.message }}
时间：{{</span>now }}
链接：https://n8n.example.com/workflow/{{ <span class="katex math inline">json.workflow.id }}/executions/{{</span>json.execution.id }}
</code></pre>

<p class="wp-block-paragraph"><strong>方式 B：健康探针</strong><br />
用外部 cron 调 n8n 自带的 <code>/healthz</code>，异常则告警；再对 Redis、Postgres 做存活检查。</p>

<h2 class="wp-block-heading">第六步：可观测性与备份</h2>

<ul class="wp-block-list">
<li><strong>日志</strong>：Worker 日志集中到 Loki/ELK，按工作流名检索。</li>
<li><strong>指标</strong>：用 Prometheus 抓 n8n/Redis 指标（若有 exporter），看队列堆积。</li>
<li><strong>备份</strong>：</li>
<li>Postgres：<code>pg_dump</code> 每日 + WAL 归档</li>
<li>Redis：<code>BGSAVE</code> 持久化（开启 AOF）</li>
<li>n8n 加密密钥：单独安全保管，丢失则凭据不可恢复</li>
<li><strong>升级</strong>：先升 Postgres 兼容的 n8n 版本，滚动重启 Worker（缩容→升级→扩容），保证 Main 不中断。</li>
</ul>

<h2 class="wp-block-heading">总结</h2>

<p class="wp-block-paragraph">生产级 n8n 的秘诀是「分而治之」：队列模式把编排与执行解耦，Worker 水平扩容扛并发，错误告警流兜住每一次失败。这样你的自动化基建才能真正「托付业务」。</p>

<h2 class="wp-block-heading">FAQ</h2>

<p class="wp-block-paragraph"><strong>Q1：队列模式一定要 Redis 吗？</strong><br />
是的，Bull 队列基于 Redis。务必给 Redis 设密码并开启持久化，否则 Redis 重启会丢在途任务。</p>

<p class="wp-block-paragraph"><strong>Q2：Worker 扩到很多会出错吗？</strong><br />
Worker 无状态，多副本安全。注意 <code>EXECUTIONS_CONCURRENCY_PRODUCTION</code> 别设过大导致单个 Worker OOM，以及外部 API 的限频。</p>

<p class="wp-block-paragraph"><strong>Q3：错误告警流本身失败了怎么办？</strong><br />
告警流也用 Error Trigger 会递归，建议告警流用独立、最简节点（纯 HTTP 推送），并对告警通道做「多通道冗余」（飞书 + 邮件），避免单一通道故障导致静默。</p>
